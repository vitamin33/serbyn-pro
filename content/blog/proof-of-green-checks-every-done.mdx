<Eyebrow>Claude Code plugin · v0.1.0 · observe week from 2026-10-04</Eyebrow>

I built proof-of-green to count how often a coding agent says "all tests pass" when no test passed after its last code change. In my first <Interim>110</Interim> turns with it installed, only <Interim>3</Interim> had a code edit, so that count cannot be made yet.

Here is what it does. A coding agent says "all tests pass", "fixed" or "done". proof-of-green looks at the same session's own record of edits and test runs and asks one question: was there a passing test run after the last code change? It does not read the conversation. Nothing leaves the machine, and it never blocks the agent.

## The short version

<Short>

**What it checks:** every "tests pass", "fixed" or "done" against the session's own record. Was there a passing test run after the last code change?

**What kind of tool:** a check that runs while the agent works. In AI engineering terms that is a runtime guardrail on agent output. It also keeps a trace of edits, test runs and claims for each session, which is observability. In warn mode it asks the agent once to show proof, a soft gate.

**Where evals fit:** evals score a model on fixed cases before a release. proof-of-green checks every real completion claim, in my real sessions, as it happens.

**What the first days say:** <Interim>3</Interim> of <Interim>110</Interim> turns had a code edit, so the headline rate cannot be computed yet. It needs roughly <Interim>30 to 50</Interim> such turns.

</Short>

This post is part of my series on false greens, the moments when a system reports success and nothing proves it. The earlier posts are linked at the end.

<Eyebrow>1 · Mechanism</Eyebrow>

## One turn, end to end

Claude Code fires hooks at fixed points in a session. A hook is a small script that Claude Code runs at that point. proof-of-green listens to four of them. Three only write facts down. The fourth, at Stop, does the checking.

<PogTurnDiagram
  caption={
    <>
      Three hooks append parsed facts (file path, exit code, pass and fail counts) to a ledger, one file per session. Raw output and prompt text are never stored. At Stop the check reads the ledger, grades the claim, and the mode decides whether anyone sees the result. Typical cost is <Interim>40 to 70 ms</Interim> per hook.
    </>
  }
/>

<Eyebrow>2 · The rule</Eyebrow>

## Everything is measured from the last code edit

A test run only counts as proof if it happened after the last change to code. Code here means an Edit or Write to a file inside the project that is not a test and not a doc.

The same claim gets a different tier depending on what happened after that line. The drawing below is an example: one claim, one failing run before the edit, four endings.

<PogTierLanes
  caption={
    <>
      Same claim, same failing run before the edit, four outcomes. D also covers "0 tests collected", exit codes hidden by <code>|| true</code>, and no test run at all. C and D are false-green candidates. Warn mode speaks only on C or D, and only when there was a code edit in that turn. A session with zero code edits never warns.

<Eyebrow>3 · Where it sits</Eyebrow>

## Evals before release, guardrails on every turn

Both answer the same question: can I trust what the agent did? They answer it at different moments. An eval runs a fixed set of cases before a release and gives a score. A guardrail runs inside real work and gives a verdict per turn.

proof-of-green is the second kind. Its own <Interim>two</Interim> eval cases test the plugin itself.

## Who gets what

<Cards>
<Card title="The engineer at the keyboard">

It catches "all tests pass" when no tests ran after the change. That saves the round trip of finding out in review or CI. It speaks rarely, in one line, and never blocks.

</Card>
<Card title="The team lead">

One number per repo and per week: how often the agent claims success without proof. That shows whether a model, a prompt or a `CLAUDE.md` change (the instruction file the agent reads) made the agent more careful or less.

</Card>
<Card title="The AI engineer">

An online metric next to offline evals. Evals say how the agent does on fixed cases. This says how it behaves in real work, with the trace to check each case.

</Card>
</Cards>

<Eyebrow>5 · Metrics</Eyebrow>

## What to measure

Value has two halves. First, how often agents claim success without proof. That is the size of the problem. Second, whether asking for proof catches real failures. That is the effect. Observe mode measures the first. Warn mode and the evals measure the second.

**The headline number cannot be computed yet.** Only <Interim>3</Interim> of <Interim>110</Interim> turns had a code edit, and only <Interim>1</Interim> claim fell inside such a turn. The A to D split needs roughly <Interim>30 to 50</Interim> turns with a code edit before a percentage means anything.

**Most of the <Interim>10</Interim> D claims are not false greens.** <Interim>Seven</Interim> are "verified" claims, and <Interim>5</Interim> claims came from sessions with no code edits at all. That fits research or review sessions, where the plugin never warns by design.

**One thing I will check when the week ends:** <Interim>1,094</Interim> Bash commands against <Interim>32</Interim> Edit and Write records. Either these sessions were mostly reading and running, or the agent edits files through Bash (`sed -i`, `cat > file`), which the plugin cannot see (decision D6). Counting the Bash commands that write files settles which one it is.

## Three ways to collect the proof

<Cards>
<Card title="Observe week" when="running · ready around 2026-10-11">

My real work, untouched. It gives the size of the problem: unsupported-claim rate, confirmed false greens, silent completions. It needs about <Interim>30 to 50</Interim> turns with a code edit, so I work normally and let it collect.

</Card>
<Card title="Backfill from history" when="optional · could run today">

Claude Code keeps past sessions on disk. A separate research script could replay them through the same parsers and give a baseline over weeks instead of days. It would be a new script outside the plugin, because the plugin never reads transcripts. It should print only totals, because those sessions include client work. I have not decided on it yet.

</Card>
<Card title="Evals in warn mode" when={<>before release · about <Interim>12</Interim> short runs</>}>

The <Interim>two</Interim> trap cases, with and without the plugin. This is the only way to show the effect, because observe mode never asks for proof. Output: verification rate and caught failures, with and without the plugin.

</Card>
</Cards>

<Callout>

**The value claim needs both halves.** The observe week, or the backfill, says how often it happens. The evals, or a few days of warn mode on my own work, say whether asking once catches real failures. One without the other is a guess.

</Callout>

## What to check on Monday

Pick one recent coding-agent session and find its last "tests pass". Then look for a test run after the last code edit. If there is none, that claim had no proof behind it.
